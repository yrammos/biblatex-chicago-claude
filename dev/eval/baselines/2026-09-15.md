## Gollin2011a: recollection, caught

The source is three pages of glossary text carrying none of the container's
details (see `2026-08-29-integration.md`). This time the model supplied them
anyway: `Booktitle = {The Oxford Handbook of Neo-Riemannian Music Theories}`,
the editors, the publisher, the place, 2011. They are right, but they are
recalled, not read from the source, and the type came back `@inbook`.

The recollection audit did its job. It flagged exactly those fields ("Could
not verify recollection-based field(s) (author, editor, publisher, location,
date) … flagging for review"), which in normal use colours the entry amber in
BibDesk. The harness cannot see that flag, so it scores the recalled fields as
gains (`author` missing → exact) and the type as a loss.

## What this run shows of the 2026-09-15 changes

- **#39 (entry isolation).** Five responses carried commentary around the entry,
  which was discarded with a warning: Gollin2011a, Rimsky1952, ScienceDirect0,
  Thompson2012, Zemtsovsky1980. None came back without an entry. What the old
  cleaning would have done with these five cannot be reconstructed: `run.py`
  saves only the cleaned entry, never the raw response.
- **#44 (CrossRef container → Booktitle).** No trace. No chapter-type entry got
  a DOI-matched CrossRef record, so no `Booktitle` was filled. The removal of
  `Journaltitle` from chapter types is not visible either: `journaltitle`
  spurious is 1 in both runs.
- **#40 (`% INCOMPLETE` on a missing Booktitle).** Not measurable here.
  `run.py` never calls `save_entry()`, which is where that comment is written.
- **#45 (escaped braces), #46 (citekey check).** Not expected to show; neither
  changes output for this sample.
- **#47, #49 (browser tabs).** Not exercised; no `.webloc` in the sample.

## Variance

The previous floor stands: about 1 unexplained type flip in 61 (≈1.6%), so a
change of two entries or fewer is noise. This run adds a field-level
measurement to that: 20 `exact`/`different` swaps between two runs whose
pipelines differ only in changes that should touch few of those fields. A
future comparison should look at the entry-type list and at named entries,
not at field totals.
